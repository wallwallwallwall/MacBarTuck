# 权限状态与发布签名

## 0.1.5 行为

- 窗口顶部显示有效权限数量；两项均通过系统检查后显示“权限已就绪”。状态栏菜单也包含两项有效状态。
- 每项权限明确显示“已生效”或“未生效”。本应用曾检测到成功时会记住历史，但历史状态不能解锁新进程。
- 设置、引导和启用收纳共用 MenuBarItemStore 持有的 PermissionManager。窗口显示时每两秒只读复检，回到应用及操作前再次检查；状态变化后重新扫描。
- 权限请求仅由明确的授权按钮触发。后台检查不弹窗，已授权时不重复请求，未生效的重复点击进入系统设置。
- 系统接受录屏请求但 preflight 尚未通过时，提示重新启动，不显示成功。
- “重新启动”先执行普通退出和现有恢复流程，再启动同一个应用路径；等待有上限，不强制结束旧进程。“定位当前应用”选中实际运行的 Bundle。

## 本机发现

2026-09-10 比对当前安装版与旧备份：临时签名的 designated requirement 是不同的 cdhash。系统列表显示的同名开关不能证明新的签名和当前进程有权访问。

此前每次编译后替换应用会改变这个身份；重新启动可处理进程缓存，但不能把旧签名的授权赋予新签名。因此未生效时需要用户在系统设置中重新添加当前应用。应用不读取或修改 TCC 数据库，不回填假的授权结果，不创建可信证书。

Apple 的 [TN2206](https://developer.apple.com/library/archive/technotes/tn2206/_index.html) 解释了签名身份和 designated requirement 的关系。该文档用于说明身份稳定性，不能代替本机具体权限状态检查。

## 发布

默认打包命令保留临时签名，适合本地测试。正式发布应使用发行者已有的 Developer ID 身份，在后续版本中持续使用同一签名身份和 Bundle ID，并单独完成 Apple 公证。

`scripts/create-dmg.sh` 支持 `BARTUCK_SIGNING_IDENTITY` 环境变量。未设置时仍使用临时签名；设置为已有身份后使用 hardened runtime 和时间戳。此路径没有在本机执行或验收，因为没有提供签名身份。脚本不会查询、创建或导入证书，也不自动公证。

14 项权限回归检查覆盖部分授权、已授权不再请求、撤销、历史与当前状态隔离、后台只读检查、接受请求但需重启及生效后清除提示。共享状态和界面检查不代表真实收纳/点击已通过；该边界仍见 runtime-qa.md。

# 刷新与布局抖动分析

2026-09-10 在已授权的 0.1.5 上点击“重新扫描”复现：界面进入“正在应用收纳布局”，项目数量从 12 变为 10，出现连续模拟拖动。

17:46:38 至 17:47:36 的日志窗口包含 54 次模拟拖动、36 次位置检查超时、19 次失败结束、4 次收纳批次和 20 次图标采集结果。这是复现前后的一分钟观察，并非全部事件都由唯一一次点击产生。

## 原因

1. 刷新结束无条件尝试自动布局。分隔条的伸缩和捕获产生新的系统窗口，又触发刷新。
2. 分隔条宽度绑定瞬时选择与图标就绪状态；扫描移动中间态时，这些值变化会反复展开和压缩菜单栏。
3. 布局同时存在单项拖动重试、批次重试和后续刷新重启，局部重试上限不能终止整体循环。
4. 原逻辑在每次收纳前后恢复其他系统项目，跨屏镜像和暂态窗口使这些恢复动作也不断失败。
5. 扫描只用瞬时坐标关联镜像，移动过程中会拆分原先确认的逻辑项目，丢失图标缓存并改变列表顺序。

## 修改

- 默认刷新只读，禁止触发布局；内部自身窗口和收尾刷新也只观察。新外部项目可以触发一次自动处理，失败后暂停自动布局，直至用户明确重试。
- 分隔条只使用已提交的隐藏区域状态；扫描/采集就绪变化不再改变物理宽度。
- 布局开始冻结目标列表，执行和收尾期间合并刷新。关闭、恢复、退出会使旧事务失效；回调必须核对事务编号。
- 单项失败结束收纳批次；位置检查有界，不重新发送同一拖动。不再自动拖动无关系统项目。
- 使用目标屏幕对应的项目镜像执行移动；没有可靠对应时拒绝，不跨屏猜测。
- 保留已经确认且窗口 ID 未变化的镜像关联；身份矛盾时解除关联。刷新保留行顺序并复用全部镜像的图标缓存。

## 日志

`~/Library/Logs/BarTuck/diagnostic.jsonl`，旧文件为 `diagnostic.previous.jsonl`。每个最多 1 MiB，最多保留两个；用户导出文件不自动删除。

事件包括 `refresh.request/result/deferred`、`separator.resize`、`layout.begin/end/cancel/restore/rehide`、`move.begin/verified/timeout/rejected.*`、`capture.completed` 及采集错误码。只记录固定事件名、时间、进程号和数值字段，没有窗口标题、应用名、图片、账号或令牌。

## 验证

- Store 集成回归先复现“只刷新列表却启动移动”，修复后连续刷新、移动中刷新、失败停止和关闭后的旧回调检查通过，共 9 项。扫描、权限、图标和移动响应使用隔离替身，不注入系统输入。
- 133 项基础测试通过，包含 3 项新增镜像关联稳定性检查。
- 日志轮换检查验证两文件上限、有效 JSON 行和最新事件留存。
- 新版已授权的双屏实机刷新仍需验证，不能以自动化结果外推为完整功能已通过。

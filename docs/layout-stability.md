# 刷新与布局抖动分析

## 0.1.15 稳定身份与 macOS 27 边界

旧刷新流程即使扫描结果没有变化，也会创建一组新的 `MenuBarItem` 对象、替换整个数组并再次发布布局与图像回调。SwiftUI 因此重新建立图标视图，状态栏控制器也重复计算隐藏区域，动态菜单项或双屏镜像更容易出现图标切换和位置跳动。

0.1.15 按稳定 ID 复用原对象，只更新实际变化的运行时字段；应用名称、应用图标与 `NSImage` 实例由解析器缓存，应用启动、退出或唤醒时才失效。刷新前后使用轻量展示快照比较，无变化时不发送 `objectWillChange`、布局状态或图像就绪回调。规则修改仍保持“先配置、后显式应用”，刷新不会触发移动。

macOS 27 的兼容策略不再把宽幅复合菜单栏宿主当作单个图标参与 AX 合并。只有尺寸接近独立状态项的 WindowServer 窗口可以补充窗口 ID 和截图；帧宽差距过大的宿主不能匹配任意 AX 子项。逐项 AX 移动另外保存最后一个可见恢复帧，隐藏后的刷新只更新当前帧，不覆盖“全部显示”所需的原位置。

## 0.1.14 显式应用与残留按键状态

2026-09-11 的已授权安装版中，用户连续将 5 个项目设为“收起”后，列表均显示“待收起”，托盘仍为 0。旧实现每修改一个规则都会在 0.3 秒后安排一次布局，逐项配置可能产生多轮全局菜单栏重排；同时，当前 macOS 会话在没有实际点击时持续返回 `left=false`、`right=true`。旧的统一按键保护会每 0.2 秒延期手动布局，因此日志中始终没有 `layout.begin`，按钮表现为无响应。

修正后，选择“收起”只保存规则并显示待应用提示，不安排移动。用户在菜单项页点击一次“应用显示方式”后才创建单个布局事务；手动布局不受残留的全局按键位影响，后台自动布局仍在真实按压时退出并记录一次 `layout.deferred_input`，不进入无限重试。通用页删除重复入口，刷新继续保持只读。

随后复测发现，第一次收纳完成后再次点击“应用显示方式”，扫描结果虽然为 `selected=5 visible=0`，旧实现仍先把隐藏分隔项从展开长度缩到 20，再把同一批项目拖回隐藏区。这会让已经收纳的图标短暂重新出现并再次飞动。修正后在任何分隔区伸缩或布局事务开始前计算实际可见数量；数量为 0 时直接记录 `layout.noop` 并提示布局已正确，不产生 `layout.begin`、`move.*` 或非零 `separator.resize`。

新增策略回归覆盖：手动应用在残留右键状态下仍可开始、后台布局在按压状态下仍会避让、修改隐藏规则在点击应用前不得启动布局，以及已经收纳时重复应用必须为纯 no-op。真实 5 项收纳、托盘点击、重新收纳和双屏结果记录在 `docs/runtime-qa.md`。

## 0.1.10 点击激活稳定性

2026-09-11 在已授权的 0.1.7 安装版复现托盘项目点击抖动。日志显示一次点击会先把目标从隐藏区移动到控制项旁，菜单关闭后再把隐藏分隔项从 `3840` 缩到 `20`、拖回目标，并重新扩到 `3840`。这会让隐藏区内其他真实菜单栏窗口短暂回到屏幕，再一起被推走；根因不是 SwiftUI 动画，而是 `reveal -> activate -> rehide` 的第二次 WindowServer 布局事务。

0.1.10 取消菜单关闭监听和自动回藏：可直接通过辅助功能或当前可见窗口激活的项目完全不移动；必须移出的项目只执行一次 `reveal`，并标记为“临时显示”。用户可在托盘或设置页显式批量重新收纳，后台刷新和新项目发现不会自动收回正在使用的临时项目。状态栏图标不再随托盘展开切换，悬停展开默认关闭，托盘动画不再使用弹簧缩放。

新增日志事件为 `activation.direct`、`activation.reveal_once`、`activation.temporary_activated`、`activation.click_failed_visible` 和 `activation.retuck_requested`。0.1.10 正常点击后不应再出现 `layout.rehide`；只有用户显式应用布局或重新收纳时才会出现 `layout.begin/end` 与必要的分隔项伸缩。

2026-09-10 在已授权的 0.1.5 上点击“重新扫描”复现：界面进入“正在应用收纳布局”，项目数量从 12 变为 10，出现连续模拟拖动。

17:46:38 至 17:47:36 的日志窗口包含 54 次模拟拖动、36 次位置检查超时、19 次失败结束、4 次收纳批次和 20 次图标采集结果。这是复现前后的一分钟观察，并非全部事件都由唯一一次点击产生。

## 原因

1. 刷新结束无条件尝试自动布局。分隔条的伸缩和捕获产生新的系统窗口，又触发刷新。
2. 分隔条宽度绑定瞬时选择与图标就绪状态；扫描移动中间态时，这些值变化会反复展开和压缩菜单栏。
3. 布局同时存在单项拖动重试、批次重试和后续刷新重启，局部重试上限不能终止整体循环。
4. 原逻辑在每次收纳前后恢复其他系统项目，跨屏镜像和暂态窗口使这些恢复动作也不断失败。
5. 扫描只用瞬时坐标关联镜像，移动过程中会拆分原先确认的逻辑项目，丢失图标缓存并改变列表顺序。

## 修改

- 默认刷新只读，禁止触发布局；内部自身窗口和收尾刷新也只观察。新外部项目可以触发一次自动处理，失败后暂停自动布局，直至用户明确重试。
- 分隔条只使用已提交的隐藏区域状态；扫描/采集就绪变化不再改变物理宽度。
- 布局开始冻结目标列表，执行和收尾期间合并刷新。关闭、恢复、退出会使旧事务失效；回调必须核对事务编号。
- 单项失败结束收纳批次；位置检查有界，不重新发送同一拖动。不再自动拖动无关系统项目。
- 使用目标屏幕对应的项目镜像执行移动；没有可靠对应时拒绝，不跨屏猜测。
- 保留已经确认且窗口 ID 未变化的镜像关联；身份矛盾时解除关联。刷新保留行顺序并复用全部镜像的图标缓存。

## 日志

`~/Library/Logs/BarTuck/diagnostic.jsonl`，旧文件为 `diagnostic.previous.jsonl`。每个最多 1 MiB，最多保留两个；用户导出文件不自动删除。

事件包括 `refresh.request/result/deferred`、`separator.resize`、`layout.begin/end/noop/cancel/restore/rehide`、`move.begin/verified/timeout/rejected.*`、`capture.completed` 及采集错误码。只记录固定事件名、时间、进程号和数值字段，没有窗口标题、应用名、图片、账号或令牌。

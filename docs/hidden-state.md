# 实际收纳状态

## 0.1.17 macOS 27 状态语义

- 在 macOS 27 及后续版本，“已收纳”表示目标在所有活动显示器上的遮罩窗口均已创建、位置已核对且当前可见；只有保存了“收起”规则但遮罩未建立时仍显示待应用或失败，不会提前进入托盘。
- 原生系统图标仍由所属应用维护在遮罩下方，MacBarTuck 不再修改复合菜单栏宿主的位置。用户看到的菜单栏位置应为空白，托盘继续显示应用自身图标用于识别和激活。
- 关闭收纳、选择“全部显示”、规则改为常显、项目退出、屏幕录制权限失效或 MacBarTuck 退出时，遮罩会同步移除，原图标恢复可见。
- 主屏和扩展屏必须同时建立遮罩才算成功；任何一块显示器缺少可信位置都会标记为收纳失败，不会宣称部分成功。

## 本机复现

2026-09-10 北京时间（UTC+8）18:28，两次手动收纳均先移动 Clock 窗口，位置确认超时，整个批次 moved=0。旧版托盘使用“选择了收起或已在屏外”的并集，所以原菜单栏仍显示时也会重复展示图标。

18:32 将时钟设为“始终显示”后再进行一次收纳：Snipaste、输入法、ChatGPT、微信、Clash Verge 共 5 个项目逐个确认移动，moved=5、remaining=0。随后只读核对两屏的 10 个窗口，全部移出显示器边界；再点击刷新没有新 move.begin 或 layout.begin 事件。这证明 0.1.6 在排除时钟后能完成这次收纳，并不代表全部应用和系统配置均已验收。

诊断 JSONL 使用 UTC：上述成功操作对应 10:32:35 至 10:32:40Z。

## 0.1.7 修正

- 系统 Clock 是保留项，旧隐藏规则不会覆盖它；Wi-Fi 等其他可配置项保持原规则语义。
- 逻辑项目汇总各屏幕窗口的真实可见状态。仅全部已确认隐藏时标记已收起；一份可见则为部分可见；缺失窗口记录为待确认。
- 托盘不再依据期望规则提前加入项目。列表保留显示方式，并单独显示已收起、待收起、收起失败或待确认。
- 布局结束读回真实窗口，失败时不会宣称收纳成功，刷新仍为只读。
- 增加旧行为先失败的 Store 回归：一个仍可见但规则为收起的项目不能出现在托盘中。

## 验证边界

已有 5 个应用的成功收纳是在保持原授权的 0.1.6 上完成。0.1.7 的托盘筛选和状态汇总通过自动化及构建检查，未替换当前运行版本，以保留用户刚恢复的授权和实际工作状态。点击转发、更多系统版本及完整冷热插拔场景仍需继续验收。
